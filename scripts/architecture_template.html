2 · One request, step by step

What happens when you open an AI-live scenario (for example S3) and click Run AI correlation. File names are real; open them alongside.

  1. Browser · app/src/lib/cache.ts
    The app loads its data

    Vite bundles every bundle.json into the page. Each holds @@BUNDLEKEYS@@. For AI-live scenarios diagnosis is null: there is no stored answer to show.

  2. Browser · app/src/App.tsx line 27
    Prefetch starts as soon as the scenario is on screen

    if (bundle.meta.mode === 'ai-live') ensureDiagnosis(slug, bundle.events). This fires while you are still looking at Screen 1, so the ~70 s call is usually finished before you click. app/src/lib/liveCache.ts keeps one in-flight request per scenario and remembers the result.

  3. Browser · app/src/lib/ai.ts fetchDiagnosis
    Send the evidence pack to your own server

    POST /api/diagnose with { slug, events[] } (see block A below). About @@INCHARS@@ characters of JSON.

  4. Vite · app/vite.config.ts
    The proxy forwards it

    The browser only talks to localhost:5173. The dev server forwards anything under /api to http://localhost:8787, so there is no cross-origin setup.

  5. Server · server/index.js app.post('/api/diagnose')
    Check the body, then run analyse() inside respond()

    respond() is the safety wrapper: it times the call, saves a success to server/cache/, or on any failure replays the saved answer (labelled server-cache).

  6. Server · buildInput(events)
    Turn events into the text the model reads

    Splits the pack into rule_hits (alerts a rule already fired) and context (records fetched around them) and writes both as labelled JSON text (block B). The prompt (prompts/analyst-system.md, read once at startup) becomes the instructions.

  7. Server · callFoundry()
    The outbound call

    Waits for a free slot (at most FOUNDRY_MAX_CONCURRENT=2 calls at once), then POST {FOUNDRY_ENDPOINT}/responses with headers api-key and authorization. On HTTP 429 it waits (the retry-after header, else 20 s then 40 s) and retries twice. Timeout 240 s. A response with status incomplete is treated as an error.

  8. Model
    Reasoning

    GPT-5 at reasoning effort low reads the rules-on-top prompt plus the pack and writes back one JSON document. Typical latency ~70 s for a 260-event pack.

  9. Server · parseJson(), validate()
    Never trust the reply

    Strips code fences and parses. If the JSON is malformed it asks once more with the parse error. Then checks required keys, 2 to 4 hypotheses, non-empty supports/contradicts, and that every cited event_id exists in the pack. Failures trigger one retry with the error list appended.

  10. Server · sanitise()
    Facts are rebuilt by code, not taken from the model

    The timeline is rebuilt from the pack using only the event ids the model chose, so it cannot alter a time, source or text. Uncitable evidence is dropped. Only the earliest first-symptom flag is kept. requires_approval is forced true. Warnings are added for a blast-radius number found in no event and for an event cited on both sides.

  11. Server · respond()
    Wrap, save, return

    Adds _meta { source:'live', model, latencyMs, warnings }, writes server/cache/<slug>.diagnosis.json, and returns it to the browser.

  12. Browser · liveCache.ts → screens/AiView.tsx
    Render

    The result is stored; Screen 2 draws the seven panels from it and shows Reasoning: Live · gpt-5. If it came from the server cache the label reads Server cache with an amber banner. The rule counts on screen come from the bundle, not the model.

  13. Human · components/ApprovalDialog.tsx
    The gate

    The recovery button is disabled until an approver name and a reason are entered; only then is a logged action record shown. Nothing in this project executes a real action.

  14. Late evidence · POST /api/diagnose/late-evidence
    "Inject late evidence"

    The browser sends the same pack, the late event and the diagnosis currently on screen (block D). The server appends the late event, sends the prompt plus prompts/late-evidence.md, and computes rank_before, rank_after and new_event itself; only the explanatory sentences come from the model.

Why each prompt rule exists

RuleThe failure or requirement behind it
Rules-on-top: you receive rule_hits and context; do not detectThe client already has 300–400+ rules. The AI must explain what they mean, never re-detect or replace them.
Every hypothesis needs supports and contradicts, each citing a real event_idAn empty "contradicts" column looks like assertion, not analysis. Citations are checked by the server.
Hypotheses are rival explanations of the same incident; unrelated problems go to ruled_outFirst S5 run promoted an unrelated "Plant field missing" mapping error to a second hypothesis and proposed rolling back an unrelated change.
A change is a cause only if linked in time and componentSame failure: an approved change merely coincided with unrelated alerts.
First symptom includes precursors on the affected component or a shared dependencyFirst S5 run marked the first failing exchange, not the cache pod restart 35 minutes earlier.
Count only the incident's own flows and name the statusS3 reported 493 "stuck" exchanges, which was the in-progress count; the failed count was 279 (cumulative 318).
Cite each event on one side only; High confidence only when the deciding check is doneThe model listed the same evidence as both support and contradiction, and called an untested assumption "High".
Absence is evidenceS2 (nothing arrives) and S4 (a half-flow that never starts) are only solvable by noticing what did not happen.

5 · How the data is made (offline)

Five commands, run in this order, deterministic (two runs give identical output). Each reads the previous step's files.

CommandReads → writesWhat it does
python generator/generate.pygenerator/scenarios.py → data/<slug>/*.ndjson|json|csvBuilds synthetic raw files in each source's own format from the declared scenario spec, with 60 minutes of baseline and each planted contradiction as a real record. MFT timestamps are written with no timezone offset on purpose.
python normaliser/normalise.pyraw files → data/<slug>/normalised-events.jsonParses every format into one event list: UTC timestamps, MFT local time resolved, service aliases resolved, severity to 1–4, exchange ids threaded. Marks each event rule_hit (something a rule already fired) or context. Computes the explicit absence events (e.g. "inbound exchanges: 0, baseline 180").
python scripts/find_anchors.pynormalised events → anchors.jsonFinds the key event ids (first symptom, contradictions, decisive evidence, late event) so they are always kept.
python scripts/build_alert_feed.pyraw files → app/src/data/<slug>/alert-feed.jsonScreen 1 only: the 147-row alert stream and the Sonar dashboard block (KPI tiles, exchange rows, traces). The model never sees this.
python scripts/build_bundles.pyevents + anchors + feed (+ authoring/<slug>.json if present) → bundle.json and evidence-pack.jsonBuilds the evidence pack and validates. If an authoring file exists the scenario is stored (every cited id must resolve, every hypothesis needs contradicts); otherwise it is ai-live with diagnosis: null.

The evidence pack (what the model gets) — selection rules, all code

  1. Rule hits: every distinct one; identical repeats collapsed into one event that states the count and first/last time. The two standing-noise alerts are included so the analyst can dismiss them.
  2. Anchors: every key event id, individually and uncollapsed.
  3. Computed summaries: code-computed context (silence, heartbeat absence, stalled exchanges, "N failed with identical reason across M projects"). This is where absence is stated as a fact.
  4. Changes, MFT rows, ticket updates: all of them (there are few).
  5. Relevant context: remaining events in scope, sampled evenly until the pack holds roughly 120 to 300 events.

Result for @@SLUG@@: @@NPACK@@ events (@@NRULE@@ rule hits + @@NCTX@@ context), about @@INCHARS@@ characters as JSON.

What the errors mean

MessageMeaning and what to do
429 … rate limit exceededToo many model calls at once. The server already waits and retries twice; if it still fails it replays the saved answer. Avoid switching scenarios rapidly.
model output failed validationAfter one retry the reply still lacked required fields. Run again; check prompts/ if it repeats.
model response incompleteThe model ran out of output budget. Retry, or lower the reasoning effort.
FOUNDRY_ENDPOINT and FOUNDRY_API_KEY are not both setFix server/.env and restart the server (it reads the file only at start).
Amber "Replayed from last successful live run"The live call failed; you are seeing the saved answer. The banner lists the failure reason.

9 · Guardrails, all in code

GuardrailWhere and why
Citations must exist in the packvalidate() + sanitise(). One retry with the errors fed back; uncitable evidence is dropped, never invented.
Timeline rebuilt from the packsanitise(). The model picks event ids; code supplies the time, source, component and text.
Approval forced onsanitise() sets recovery.requires_approval = true regardless of the reply. The UI adds the named-approver gate.
Rank change computed by codeLate-evidence route: rank_before from the previous diagnosis, rank_after from the new one, new_event from the input.
Grounding warningsA blast-radius number appearing in no event, an event cited on both sides, more than one first symptom (earliest kept).
Bounded concurrency + 429 retryacquire()/release() around callFoundry; waits on retry-after.
Fallback, never fabricationrespond() replays the last good answer with a visible label; if none exists it returns an error and the UI shows it.
Rule counts come from codebuild_bundles.py counts distinct rule ids in the pack; the UI never uses a number the model wrote.
